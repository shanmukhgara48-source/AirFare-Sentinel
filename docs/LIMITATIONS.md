# Known Limitations and Assumptions

**APIx: India Airfare Price Index**

---

## Data limitations

### 1. The bundled demo data is synthetic

The bundled dataset of 23,558 observations is generated by
`backend/app/seed/generate_sample_data.py` with a fixed random seed (26056).
Carrier codes (SA1, BW2, NS3, CE9) are fictional.

**Impact:** Demo index values demonstrate the methodology but do not reflect
actual airfare trends. The application also includes a credential-gated Amadeus
adapter, but no live claim is made unless a provider fetch succeeds and rows are
stored with `source_type=live`.

### 2. Prototype route basket

The 14 directional routes (7 city pairs) cover major trunk routes but not the
full domestic network. Many commercial airports are outside the prototype
basket. It uses illustrative traffic proportions. The weights are not current
official DGCA route shares.

**Impact:** The headline index reflects the basket routes, not the full market.
Production would use a complete, current authoritative route-volume source with
regular weight updates.

### 3. No scheduled collection

Data is loaded manually through the sample button, CSV upload, or a
credential-gated provider fetch. There is no scheduler or continuous collection
pipeline. The Amadeus test environment has limited Indian domestic coverage.

**Impact:** Even with credentials, provider rows are point-in-time quote
snapshots, not a continuously refreshed index or transaction record. Production
would require licensed coverage and scheduled collection.

## Methodological assumptions

### 4. Fixed base period (no chain linking)

The index uses a fixed base period (the first observation date in the dataset).
There is no annual chain linking or base-year rotation.

**Impact:** Over long periods, the fixed-base Laspeyres index has a known
upward substitution bias — passengers shift to cheaper options, but the index
still weights the original basket. Production would implement annual chain
linking per CPI best practice.

### 5. Equal lead-bucket and fare-class weights

Within a route, all 5 lead-time buckets and all 4 fare classes receive equal
weight. In reality, most passengers book 15–30 days ahead and fly economy
saver.

**Impact:** The headline index may overweight business class and last-minute
bookings relative to actual passenger behaviour. Production would derive
sub-route weights from booking data.

### 6. No seasonal adjustment

The index series is raw — festive surges (Diwali, Christmas), weekday/weekend
effects, and school holiday patterns are visible but not removed.

**Impact:** Month-on-month comparisons may reflect seasonal patterns rather
than genuine price trends. Production would apply X-13ARIMA-SEATS seasonal
adjustment.

### 7. No imputation for missing cells

If a comparability cell has no observation in a period, it is excluded from
the index. No carry-forward, no interpolation, no estimation.

**Impact:** The headline index for that period reflects fewer cells, and the
coverage percentage drops. This is a deliberate transparency choice — we
report the gap rather than inventing a price. The quality flag system (GREEN /
AMBER / RED) alerts users to low-coverage periods.

### 8. Geometric mean requires positive fares

The Jevons formula uses geometric means, which are undefined for zero or
negative values. All fares must be strictly positive (enforced by validation
rule `NON_POSITIVE_FARE` and database CHECK constraint `base_fare > 0`).

**Impact:** Free tickets, credits, or negative adjustments cannot be included
in the index. This is standard practice for price indices.

## Technical limitations

### 9. SQLite single-writer constraint

SQLite allows only one writer at a time. Concurrent data loads will queue.

**Impact:** Not an issue for demo or single-user operation. Production would
use PostgreSQL for concurrent access.

### 10. In-memory computation

The index is recomputed from raw observations on every API request. There is
no caching, no materialized views, no pre-aggregation.

**Impact:** Response time scales with observation count. The 23,558-row demo
panel remains practical for local use; much larger panels would need caching
(Redis), materialized views, or pre-computation.

### 11. No authentication or authorization

All API endpoints are open. The CORS policy allows `localhost:5173` only, but
there is no login, no API key, no role-based access control.

**Impact:** Acceptable for demo. Production would add MoSPI SSO or OAuth2,
with separate analyst and admin roles.

### 12. No HTTPS

The development server runs on HTTP. No TLS certificates are configured.

**Impact:** Demo-only. Production would terminate TLS at a reverse proxy
(nginx or cloud load balancer).

### 13. Process-local live-fetch status

The most recent live-fetch execution summary is held in backend process memory.
Stored observations and their provenance remain in SQLite, but the fetch summary
is cleared when the backend restarts.

**Impact:** This does not affect the offline demo path. Production would persist
job status in the database or a queue-backed job table.

## Scope boundaries

### What this prototype is

- A **methodology demonstration** — showing that the Laspeyres/Jevons approach
  works for airfares
- A **working software system** — 24 API endpoints, 10 frontend routes, 447 tests
- A **statistical tool** — transparent, reproducible, auditable

### What this prototype is not

- An **official statistical release** — the data is synthetic
- A **production system** — no auth, no HTTPS, no scheduled collection
- A **forecast** — the index measures what happened, not what will happen
- A **recommendation engine** — it does not tell travellers when to book

## Risk register

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Demo data looks unrealistic | Low | Fares follow log-normal distributions with realistic lead-time sensitivity; fictional carrier codes prevent confusion with real airlines |
| Index formula challenged | Medium | Focused engine and integration tests verify statistical properties; methodology page explains every step |
| Missing data questioned | Low | Quality flags visible on dashboard; no imputation policy explained in methodology; coverage percentage shown on stat card |
| "Why not just average fares?" | High | Demo script includes this Q&A; booking-mix confounding explained with concrete example |
| Network failure during demo | Medium | Sample data, dashboard assets, and calculations are local; live fetch remains optional |
